# Dialog

Dialog is a modal window for a focused task, such as editing a record or reading terms. It is a
native `<dialog>` opened with `showModal()`, so the browser makes the page behind it inert, puts
it in the top layer and draws the backdrop. You pass a `title`, an optional `description`, the
body as children and a `footer` of actions. `DialogClose` is a Button that closes the nearest
dialog. For a destructive confirmation, use [AlertDialog](?path=/docs/components-alertdialog--docs).

## Usage

```tsx
import 'greenility-ui/styles.css'; // once, at the root of your app
import { Button, Dialog, DialogClose, TextField } from 'greenility-ui';

<Dialog
  title="Edit site details"
  description="Changes apply to every report that includes this site."
  trigger={<Button>Edit site</Button>}
  footer={
    <>
      <DialogClose>Cancel</DialogClose>
      <DialogClose variant="primary" onClick={save}>
        Save
      </DialogClose>
    </>
  }
>
  <TextField label="Site name" defaultValue="Rotterdam warehouse" />
</Dialog>;
```

The `trigger` is cloned with an `onClick` that opens the dialog. Your own `onClick` on it runs
first; call `event.preventDefault()` there to stop the dialog opening.

### Long scrolling body

The header and footer stay in view and only the body scrolls. A scrolling body becomes a tab
stop, so keyboard users can scroll it with the arrow keys. It is a group named by the title.
When the first control in the body is out of view, the body itself gets focus on open, so
reading starts at the top.

### Controlled

Pass `open` and `onOpenChange` to open the dialog from anywhere, without a `trigger`.
`onOpenChange` receives only the requested state: `false` from the close button,
`DialogClose`, <kbd>Escape</kbd> or a backdrop click.

## Props

### Dialog

The ref and any other props go to the native `<dialog>`. The body is unmounted while the
dialog is closed, so its state resets on every open.

<ArgTypes of={DialogStories} />

### DialogClose

A Button that closes the nearest Dialog or AlertDialog after its own `onClick`, unless that
handler calls `event.preventDefault()`. It takes every Button prop and defaults to
`variant="secondary"`. It throws when rendered outside a dialog.

## Accessibility

**Pattern.** [WAI-ARIA APG Dialog (Modal)](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/),
met by the native `<dialog>` element opened with `showModal()`. The browser makes everything
outside it inert, so there is no JavaScript focus trap.

**Keyboard.**

**Focus.**

- On open, focus goes to `initialFocusRef` if you set it. Otherwise it goes to the first
  focusable element in the body, then in the footer, then to the close button, then to the
  panel itself. Body content is preferred over the close button in the header, so users start
  in the content.
- If the body scrolls and its first focusable element is out of view, the body gets focus
  instead, so reading starts at the top. On a very short screen, where the whole panel
  scrolls, the panel gets focus for the same reason.
- On close, focus returns to the element that had focus before the dialog opened (usually the
  trigger), or to `returnFocusRef` when you set it.
- If the dialog unmounts while open, for example on a route change, it still closes and returns
  focus.

**Pointer.** A click on the backdrop closes the dialog. A drag that starts inside the panel and
ends on the backdrop does not count, and a click that closes an open Menu or Select inside the
dialog does not also close the dialog.

**Scroll and reflow.** While a dialog is open, the page behind it does not scroll. This is done
in CSS with `scrollbar-gutter: stable`, so the layout does not shift. At 320 CSS pixels wide or
400% zoom, the panel fills the width and the dialog scrolls instead of clipping. On short
screens (30rem high or less), the whole panel scrolls, not only the body. The footer buttons
wrap onto new lines when there is not enough room.

**Screen reader.**

- The dialog is announced as a dialog, named by `title` (an `<h2>`) through
  `aria-labelledby` and described by `description` through `aria-describedby`.
- The page behind is removed from the accessibility tree while the dialog is open.
- The close button is announced as "Close" (or your `closeLabel`). Its tooltip is decorative.
- Toasts shown while the dialog is open move into the dialog, so they stay clickable and are
  still announced.

**What you must provide.**

- A meaningful `title` that names the task, such as "Edit site details". An empty title logs a
  console warning, because the dialog would have no accessible name.
- A `description` when the user needs context before acting.
- At least one way to finish the task, usually a `DialogClose` and a primary action in the
  `footer`.
- A `returnFocusRef` when the action removes the trigger.

**Verified.** Automated: unit tests with axe, plus axe on every story in light and dark themes
in Chromium, Firefox and WebKit. Not yet verified with NVDA, JAWS or VoiceOver.

## Do / Don't

**Do**

- Use a Dialog for a short task that needs the user's full attention.
- Write a title that names the task, and keep the footer to one or two actions.
- Use `DialogClose` for Cancel and for actions that should close the dialog.
- Set `returnFocusRef` when the action deletes the element that opened the dialog.
- Use an AlertDialog for destructive confirmations.

**Don't**

- Don't open a dialog on page load or without a user action.
- Don't put long, multi-step flows in a dialog. Use a page.
- Don't use a generic title such as "Dialog" or "Are you sure?".
- Don't stack more than two dialogs.
- Don't render your own `open` attribute on the `<dialog>`. Control it with `open` and
  `onOpenChange`.
